# Internationalization

## Initial locales

- `en`
- `es`

Architecture must support additional locales without component changes.

## Rules

- No user-facing hardcoded strings in feature components.
- Locale choice is persisted in profile/local settings.
- Browser locale may select the initial default.
- User can change language from Profile/Settings.
- Missing translation falls back to English and should be detectable in development.

## Basketball content

Domain entities use stable IDs and translation keys.

Example:

```json
{
  "id": "def.rebound.find-player-first",
  "translationKey": "guidelines.def_rebound_find_player_first"
}
```

English:

```json
{
  "guidelines": {
    "def_rebound_find_player_first": {
      "title": "Find your player first",
      "instruction": "When the shot goes up, locate your opponent before tracking the ball.",
      "cue": "SHOT → PLAYER → CONTACT → BALL"
    }
  }
}
```

Spanish:

```json
{
  "guidelines": {
    "def_rebound_find_player_first": {
      "title": "Localiza primero a tu rival",
      "instruction": "Cuando salga el tiro, localiza a tu rival antes de seguir el balón.",
      "cue": "TIRO → RIVAL → CONTACTO → BALÓN"
    }
  }
}
```

## Dates/numbers

Use `Intl` APIs and locale-aware formatting.
Do not manually concatenate localized dates.

## Translation quality

Basketball terminology must be reviewed editorially. Do not assume literal translations are correct.
